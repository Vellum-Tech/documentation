## What a project is

A **project** is one piece of impact-measurement work you do for one organisation, covering one reporting period. If you have been engaged to produce a FY2026 impact report for a food-rescue charity, that is a project. If the same charity also asks for a separate cost-benefit analysis of one program, that is a second project.

Everything the engagement produces lives inside the project: the documents you gather, the impact model you build, the quantities the client measures, the valuations the engine computes, the register of sources you review, and the report you eventually sign off. Vellum keeps all of it in one record so that, months later, anyone can open the project and trace a number in the report back to the document it came from.

Three things are true of every project and worth knowing up front:

- **A project always belongs to an organisation.** You choose the organisation when you create the project, and you cannot invent one on the spot. It has to exist as a record first. See the [Organisations](/guides/organisations) guide.
- **A project always covers a period.** Dates matter, because the quantities you record are measured over that period, and the report says so.
- **No one ever types a dollar figure into a project.** Money is computed, never entered. You supply the evidence and the method, and the calculation engine produces the number. This one rule shapes almost every screen you will meet.

## Creating a project

From the **Projects** page, select **New project**. The dialog asks for four things:

- **Organisation**: search and pick the organisation the work is for.
- **Title**: what you would call this piece of work, such as "FY2026 Impact Report".
- **Period start** and **Period end**: the reporting period. These default to the current Australian financial year (1 July to 30 June), which is right most of the time.
- **Report type**: **Impact**, **SROI** or **CBA**. This is a light label for what kind of report you are producing, and you can change it later.

Select **Create project** and Vellum takes you straight into the new project's record. Everything else (description, methodology, purpose, audiences) is refined on the record itself, so there is no long form to fill in before you can start work.

New projects always start at the **Discovery** stage.

### Finding a project again

The **Projects** page lists everything you have on. You can search by project title or organisation, filter by **Stage** and **Report type**, sort by any column, and switch between a list and a card grid with the view toggle. The columns are **Project**, **Organisation**, **Stage**, **Report type**, **Period** and **Total value**. That last one is the total impact value the project reports for the period, once there is one.

Selecting one or more rows with their checkboxes reveals a bulk **Delete** action. Deletion is permanent, and a project that already carries calculation data is protected: Vellum refuses to delete it and tells you why.

## The project record, tab by tab

Opening a project shows a record with a header (breadcrumb, tabs, the stage control and a **⋯** menu) over the tab you are currently in. The tabs run in workflow order, so left to right is roughly the order you will work in.

There is also a small question-mark button in the header, **How a report comes together**, which lists the six steps of a report and jumps you to the tab where each one happens. It is worth opening the first few times.

### Overview

The project's front page, and the only tab that is purely about the engagement itself rather than the measurement work.

At the top sits the project's hero card: the title (select it to rename in place), the organisation it belongs to, the period, a progress bar across the lifecycle, and the current stage.

Below that:

- **Details**: **Period start**, **Period end**, **Report type**, **Locale** (which regional English the report is written for, such as en-AU) and a free-text **Description** of what this project measures and reports.
- **Reporting methodology**: the report's method, pinned and attributable. Covered in its own section below.
- **Purpose & audiences**: the **Primary purpose** of the report and the **Audiences** it is written for, chosen from the organisation's own lists. If the one you need is not there yet, you can type it and add it inline. It is saved onto the organisation's record so the organisation stays the single source of truth, and it is then available to that organisation's other projects.

### Data room

The gathering surface: what you have, what you are still waiting on, and what it all says. The rail on the left holds five sections: **Files**, **Data requests**, **Outcomes**, **Activities** and **Beneficiaries**.

This is the organisation's one document vault seen through this project's lens, and the entity registers fill up as you build the model. It has its own guide: see [Data room and documents](/guides/data-room-and-documents).

### Model

Where you build the impact model. This is the structural phase, and it is covered in full below.

### Quantify

Where the numbers live: the measured quantities the client reports, the Workbench that computes value from them, and the reference rates those computations rest on. Covered below, with the deep mechanics in [Workbench and valuations](/guides/workbench-and-valuations).

### Sources

The project's source register: every data input, proxy, claim and asset traced to a source and a named responsible person.

Most rows arrive here on their own. Each time you bind a piece of evidence in the Workbench, an entry is captured automatically, recording where the input came from and what it was used in. You can also add entries by hand with **Add source**.

The tab's job is the human pass. Each row carries an **ID**, the **Value / claim**, its **Type**, the **Responsible** person and a **Status** you set from a pill on the row. The header keeps a running score, such as "8 of 12 reviewed · 2 incomplete", and any row missing a field that sign-off will require is flagged with a warning triangle. Nothing here is blocked. The flags simply tell you what is still outstanding.

This register sits after Quantify on purpose. Its rows mostly capture themselves during valuation, and reviewing them is the last human step between the numbers and the report. Report sign-off waits on it.

### Report

The deliverable: a draft report built entirely from the engine's valuation lines. It shows a **Draft** badge and the time it was generated, the project title and organisation, the headline **Total valued impact (draft)**, then **Impact by activity**, the individual **Valuation lines**, **Assumptions & sources** and any outstanding **Data gaps**.

Nothing on this tab is editable, and that is deliberate. Opening it computes nothing and stores nothing. It is a projection of the calculation as it currently stands, so it regenerates every time the calculation changes. Writing and editing report narrative is coming soon. Today the tab shows the generated draft.

### Audit trail

Every change made to this project, in order: the project record itself, activities, beneficiaries, valuation lines, impact accounts, sources, data gaps and sign-off events. The trail is captured at the database level rather than by any one screen, so a change made in the Workbench, made by an automated tool, or made directly against the data all appear here identically. Nothing edits or hides it.

## Stages, the workflow map and locking

### The stage

Every project sits at one of ten stages, shown as a coloured pill in the record header and on the projects list:

**Discovery** → **Research** → **Proposal** → **Engaged** → **Data collection** → **Modelling** → **Calculation** → **Drafting** → **Review** → **Published**

The stage is yours to set: select the pill and choose another. Any stage can be chosen at any time, and Vellum never forces you forward or stops you going back. The stage is how you and your colleagues tell at a glance where an engagement is up to, and it drives the progress bar on the Overview hero card.

Sometimes a small caption appears beside the stage, such as **· Gated**. That is the calculation engine reporting its own sub-state underneath your stage. It is extra detail, not a second status, and it never overwrites what you chose.

### The workflow map

The **How a report comes together** dialog in the header is the orientation map: six steps, each linking to the tab where it happens.

1. **Gather the evidence** (Data room): upload the client's documents and chase what is missing.
2. **Build the model** (Model): the Chart of Impact Accounts.
3. **Record the numbers** (Quantify): the client's measured quantities. Never dollars.
4. **Value it in the Workbench** (Quantify): bind each operand, and the engine computes the dollars.
5. **Review the sources** (Sources): every input approved by a named person.
6. **Generate the report** (Report): a read-only projection, walked through sign-off.

Each step also carries a faint line mapping it back to the equivalent column in the spreadsheet workbench consultants used before Vellum, which is useful if you are coming across from that way of working. The map is orientation only. It never gates anything and never reorders your work.

### Locking

At some point the calculation has to stop moving so the report can be final. That is **locking**, and it happens from the Workbench's **Lock** button.

Locking is a governance act, so it asks for your name (and optionally your role) and records it. It is not automatic and never attributed to AI. Once locked:

- The project reads as **Locked** in the Workbench, and other surfaces show a small **Gated** tag where their add or edit controls used to be.
- You can no longer add impact accounts, edit weights, record new quantified outputs, or compute new valuations.
- Everything stays fully readable. Locking freezes the work. It does not hide it.
- The stage pill picks up the **· Gated** caption.

<Warning>
Treat a lock as permanent. Unlocking is possible only through the engine and should be genuinely exceptional.
</Warning>

Note that this project-level lock is separate from the smaller **Lock methodology** action on the Overview tab, which freezes only the choice of reporting methodology.

## Choosing the reporting methodology

The **Reporting methodology** card on the Overview tab records *how* this report is done: the recognised approach you are following, the version of the standard you are following it against, and why you chose it. It is decided up front, before outcome valuation begins, because the method shapes what counts as a defensible number.

Vellum suggests six well-known approaches, each with guidance describing what it is best suited to, what it typically outputs and how a reader should interpret it:

- **SROI / sSROI**
- **Cost-Benefit Analysis (CBA)**
- **Impact Weighted Accounting**
- **Choice Modelling / Stated Preference**
- **Public Value / Policy Evaluation**
- **Natural Capital / Environmental Accounting**

These are suggestions, not a closed list. If your firm uses a bespoke approach, type its name and that wins.

Alongside the methodology you record a **Version / standard** (for example, "Social Value International Standard 2021"), a **Rationale** for why this methodology suits this project, and **Chosen by**, a named person. Vellum will not accept a methodology that nobody is accountable for.

Once the version and rationale are filled in, **Lock methodology** becomes available. Locking freezes the choice and its version for this report, recorded against your name. It matters because the sign-off ladder cannot reach **Method-approved** while the methodology is still unlocked. Unlocking afterwards requires both a name and a written reason, and the override is recorded.

<Note>
A word on the two that look alike. The **Report type** field on the **Details** card (Impact, SROI, CBA) and the **Reporting methodology** card are related but not the same thing. Report type is a quick label for what kind of report this is, used mainly for filtering the projects list. The methodology card is the governance record, covering the specific approach, its version, the reasoning and the person accountable, and it is the one sign-off checks.
</Note>

## The Model tab: building the impact model

The Model tab holds one thing: the **Chart of Impact Accounts**. It is the heart of the project, and its structure is deliberately simple.

**One row equals one activity, one beneficiary and the aligned outcome it realises.** That triple is an *impact account*. If your youth mentoring program improves school engagement for participants and also reduces stress for their carers, that is two rows: same activity, two beneficiary-and-outcome pairs.

Each row carries:

- **Account**: an identifier Vellum assigns, so a row can be referred to precisely.
- **Activity**: what the organisation did.
- **Beneficiary**: who it accrued to.
- **Aligned outcome**: the change realised.
- **SDGs**: which Sustainable Development Goals the outcome aligns to.
- **Weight**: how the activity's value is split across those SDGs, as percentages.
- **Evidence**: how well-evidenced the outcome is, from **Measured**, **Estimated**, **Proxy**, **Placeholder** or **Future survey needed**.
- **Valued**: a tick once the row is linked to a computed valuation.

Select **Add account** to open the row editor. The **Beneficiary** and **Activity** fields let you pick something already on the project, pick from your firm's shared libraries, or type something new. When you type something new, Vellum offers to add it to the library so the next project can reuse it. Picking a library entry brings its SDG alignment with it. **Aligned outcome** works the same way, and suggests outcomes commonly associated with the activity you chose. There is also a **Resource input** field for describing what the activity costs or consumes, in words, never as an amount.

If a sensitive beneficiary group is chosen, a safeguard note appears immediately, before the group can reach a report.

### Weighting to the SDGs

Where a row aligns to several SDGs, you enter a percentage against each. Rows that share an activity pool into one group whose weights must total 100%, and a running total appears under the last row of the group. If it does not add to 100, Vellum flags it in amber but never blocks you. **Split evenly** fills an exact even split across the group if that is what you want.

Once an activity has been valued, the dollar slice each weight represents appears beside the percentage. You never type that figure: the percentage is yours, the dollars are computed.

### Working with the chart

- **Value this outcome** (from a row's **⋯** menu) sends the row to valuation. If its activity has already been valued, the row simply links to that existing valuation. Otherwise the new-valuation panel opens with the activity pre-filled.
- **Add outcome split** creates a sibling row on the same activity, so several aligned outcomes share the one pot of valued dollars.
- **Suggest accounts from valuation lines** offers draft rows for any valuation the engine has computed that the chart does not represent yet. You confirm each before it is created.
- The view options button lets you group the chart by **Activity**, **Beneficiary**, **Aligned outcome** or **Evidence status**. Grouping is a way of looking at the same rows, nothing more, and your choice is remembered per project.

No dollar amount is ever entered or shown in this tab. Value belongs to the Workbench.

## The Quantify tab

Quantify has three sections in its left rail. The tab opens on the Workbench, since that is where most of the work happens.

**Quantified outputs** is the client's measured quantities, such as meals served, hours volunteered or tonnes diverted, each with a value, a unit, a period and a source. Select **Record metric** to add one. The source is classified as a **Document extraction**, **Client upload**, **Engagement answer** or **Analyst estimate**, and you can attach a note saying exactly where the number came from. These are evidence, never report values, and they are what valuation formulas draw on. In the old spreadsheet way of working, this was the "Outcomes (quantified)" column.

**Workbench** is where value is computed. You bind each operand of a valuation formula to either a reference factor or a piece of client data, and the engine returns the figure. The Workbench also tracks data gaps, per-line review, recalculation, the project lock and the sign-off ladder. This is the deepest part of Vellum, and it has its own guide: [Workbench and valuations](/guides/workbench-and-valuations).

**Factors** is a read-only register that answers the audit question "which reference rates does this report rest on?" Each row is one factor and the exact version applied, with its source tier (**Published**, **Peer**, **Industry**, **Assumption** or **Firm-internal**) and the valuations that depend on it. Factors are maintained in the [Factor library](/libraries/factors) and bound in the Workbench, and nothing is edited here. It is the fastest way to spot a stale rate that touches several lines at once.

## The workflow from start to finish

Here is how a whole engagement runs, in the order you would actually do it.

**Set up.** Create the project against its organisation, with the right period and report type. On the Overview tab, write a short description, set the locale if the report is not for an Australian audience, and record the primary purpose and audiences. Who this report is for shapes everything downstream. Then choose the **Reporting methodology**, pin its version, write the rationale and put your name to it. Move the stage to **Engaged** when the work is on.

**Gather.** In the Data room, upload everything the client has given you and raise **Data requests** for what is missing. Move the stage to **Data collection**. As material comes in, the outcomes, activities and beneficiaries the evidence describes accumulate in the registers alongside the files.

**Model.** On the Model tab, build the Chart of Impact Accounts, one row per activity, beneficiary and aligned outcome. Set each row's SDG alignment and evidence status. Weight the SDGs where a row spans several. Move the stage to **Modelling**. This is where you decide what the report will actually claim.

**Quantify.** In **Quantified outputs**, record what the client measured over the period, with a source for each. Every number here is a count, an hour, a tonne. Never a dollar.

**Value.** In the **Workbench**, value each outcome: pick a formula, bind its operands to reference factors or to the quantities you just recorded, and let the engine compute. Move the stage to **Calculation**. As each valuation lands, its inputs appear in the Sources register and its rates appear in **Factors**, and the valued rows tick over in the Chart of Impact Accounts with their SDG dollar splits filled in.

**Review the sources.** On the Sources tab, work through the register. Confirm each entry has a value, a source and a responsible person, then set its status. Clear the incomplete flags. This is the pass that stands between the numbers and the report.

**Report and sign off.** Open the **Report** tab to read the draft the engine produced. Move the stage to **Drafting**, then **Review**. Sign-off itself runs from the Workbench as a seven-step ladder, each step owned by a named human:

1. **Draft only**
2. **Ready for client query / internal review**
3. **Client-confirmed input**
4. **Method-approved calculation**
5. **Report-ready draft**
6. **Locked final package**
7. **Auditable export bundle**

Steps have prerequisites. **Method-approved** needs the methodology locked, and the final package needs the project locked. The ceremony is described in full in [Workbench and valuations](/guides/workbench-and-valuations).

**Lock and publish.** Lock the project, produce the exports (a calculation workbook and a draft report document, both from the Workbench), and set the stage to **Published**.

## Tips and gotchas

**Deep-link to a tab.** The tab you are on is reflected in the address bar, so you can send a colleague a link that opens on the Sources tab rather than the front page.

**A project is not archived, only deleted.** Organisations can be archived. Projects cannot. If a project should not be deleted, leave it at whatever stage it stopped at.

**Purpose and audience entries live on the organisation.** Adding one from a project's Overview tab writes it to the organisation's record and then links it here. That is intentional, because the organisation is the source of truth, but it does mean the entry becomes available to that organisation's other projects too.

**Deleting an impact account does not delete its valuation.** If you remove a row from the chart, any valuation the engine computed for it is untouched. You can link a fresh row back to it, or use **Suggest accounts from valuation lines** to recover it.

**Weights that do not total 100% are flagged, not blocked.** Amber means "have another look", not "you cannot continue". But an activity whose valued dollars are not fully allocated will read oddly in the report, so it is worth clearing.

**The Sources register mostly fills itself.** Do not sit down to write it from scratch. Do the valuation work first, then come back and review what the Workbench captured.

**The Report tab never computes anything.** If a figure looks stale, the fix is to recalculate in the Workbench. The report will reflect it the moment the calculation changes.

**Locking is meant to be final.** Before you lock, check that the source review is complete, the methodology is locked, and the report reads the way you want it to. Unlocking afterwards is an engine-level intervention, not a button.

**ESG reports are not available yet.** The report type exists but its flow is parked, so it is not offered when you create or edit a project.
