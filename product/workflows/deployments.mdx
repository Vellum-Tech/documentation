When a Workflow is ready for production, you deploy it. A deployment freezes the current state of your Workflow graph — nodes, edges, prompt templates, and configuration — and exposes it as a stable, versioned API endpoint. You can promote deployments across environments, roll back to a previous release, and monitor every execution in the Vellum observability dashboard.

---

## Deploying a Workflow

<Steps>
  <Step title="Open the Deploy dialog">
    From the Workflow canvas, click the **Deploy** button in the top-right corner. The deploy dialog appears.
  </Step>
  <Step title="Name your deployment">
    Enter a unique **Deployment Name**. This slug is how you reference the deployment in SDK calls (e.g., `my-research-agent`). Deployment names are immutable once created — choose something meaningful.
  </Step>
  <Step title="Add a release label (optional)">
    Attach a **Release Tag** such as `v1.0` or `production` to make it easy to identify this version later. Tags can be promoted to new deployments without re-deploying from scratch.
  </Step>
  <Step title="Confirm and deploy">
    Click **Deploy**. Vellum validates the graph (checking for disconnected nodes, missing required inputs, and type mismatches), then publishes the deployment. You'll see the new version appear in the **Deployments** tab within a few seconds.
  </Step>
</Steps>

<Note>
  Deploying does **not** affect currently running executions. In-flight calls continue to use the version that was live when they started.
</Note>

## Calling a Deployed Workflow

Use the Vellum SDK to execute a deployed Workflow. Pass your input variables as a list of typed input objects. The response contains an `outputs` array keyed by the names of your Final Output nodes.

<CodeGroup>

```python Python
import vellum
from vellum import StringInput

client = vellum.Vellum(api_key="YOUR_API_KEY")

result = client.execute_workflow(
    workflow_deployment_name="my-research-agent",
    inputs=[
        StringInput(name="user_query", value="What are the latest trends in renewable energy?"),
        StringInput(name="max_sources", value="5"),
    ],
)

for output in result.data.outputs:
    print(f"{output.name}: {output.value}")
```

```typescript TypeScript
import { Vellum, StringInput } from "vellum-ai";

const client = new Vellum({ apiKey: "YOUR_API_KEY" });

const result = await client.executeWorkflow({
  workflowDeploymentName: "my-research-agent",
  inputs: [
    { type: "STRING", name: "user_query", value: "What are the latest trends in renewable energy?" },
    { type: "STRING", name: "max_sources", value: "5" },
  ],
});

for (const output of result.data.outputs) {
  console.log(`${output.name}: ${output.value}`);
}
```

</CodeGroup>

### Input types

Vellum supports the following input types. Match the type to the type declared in your Workflow canvas:

| SDK class | Type string | Use for |
|---|---|---|
| `StringInput` | `STRING` | Plain text values |
| `NumberInput` | `NUMBER` | Integers and floats |
| `JsonInput` | `JSON` | Structured objects and arrays |
| `ChatHistoryInput` | `CHAT_HISTORY` | Arrays of chat messages |

## Streaming Execution

For Workflows that contain LLM nodes with long outputs, use the streaming endpoint to receive Final Output values token by token as they are generated — rather than waiting for the entire Workflow to finish.

<CodeGroup>

```python Python
import vellum
from vellum import StringInput

client = vellum.Vellum(api_key="YOUR_API_KEY")

stream = client.execute_workflow_stream(
    workflow_deployment_name="my-research-agent",
    inputs=[
        StringInput(name="user_query", value="Summarise the history of the internet."),
    ],
)

for event in stream:
    if event.type == "WORKFLOW_OUTPUT":
        # Partial string value from a streaming Final Output node
        print(event.output.value, end="", flush=True)
    elif event.type == "WORKFLOW_EXECUTION_FULFILLED":
        print("\n✅ Workflow complete")
```

```typescript TypeScript
import { Vellum } from "vellum-ai";

const client = new Vellum({ apiKey: "YOUR_API_KEY" });

const stream = await client.executeWorkflowStream({
  workflowDeploymentName: "my-research-agent",
  inputs: [
    { type: "STRING", name: "user_query", value: "Summarise the history of the internet." },
  ],
});

for await (const event of stream) {
  if (event.type === "WORKFLOW_OUTPUT") {
    process.stdout.write(event.output.value ?? "");
  } else if (event.type === "WORKFLOW_EXECUTION_FULFILLED") {
    console.log("\n✅ Workflow complete");
  }
}
```

</CodeGroup>

<Tip>
  Only **string-typed** Final Output nodes stream token by token. Outputs of other types (JSON, number, etc.) are emitted as a single event once their upstream node completes.
</Tip>

## Release Management

Vellum gives you fine-grained control over which version of a Workflow is live in each environment.

### Release tags

A release tag is a human-readable label you attach to a deployment version — for example, `production`, `staging`, or `v2.1`. Tags move independently of versions: you can re-point the `production` tag to a newer version without changing any SDK call that references the tag name.

### Promoting across environments

To promote a Workflow from staging to production:

1. Open the **Deployments** tab for your Workflow.
2. Find the version you want to promote.
3. Click **Promote**, select the target environment, and confirm.

The selected environment's active deployment is instantly updated. No re-deploy is required.

### Rolling back

If a new deployment causes regressions:

1. In the **Deployments** tab, locate the previous stable version.
2. Click **Set as Active**.
3. All new API calls immediately route to that version.

<Note>
  Rollback is instantaneous and does not affect in-flight executions.
</Note>

## Monitoring Executions

Every execution of a deployed Workflow is captured in Vellum's observability dashboard. You can inspect:

- **Input and output values** for every run.
- **Node-level traces** showing each node's inputs, outputs, latency, and token usage.
- **Error details** when a run fails, including which node raised the error.
- **Aggregate metrics** — latency percentiles, error rate, and cost over time.

Navigate to **Observability → Workflow Executions** in the left sidebar to explore your production traces.
