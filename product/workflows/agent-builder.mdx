Agent Builder is the part of Vellum Workflows designed for building autonomous AI agents — applications where an LLM decides at runtime which tools to call, processes the results, and repeats until the task is done. Rather than you hard-coding a fixed sequence of steps, the agent figures out the sequence on its own. This page explains how the Agent Node works, how to define tools for it to call, how the iteration loop operates, and patterns for common agent use-cases.

---

## What Is the Agent Node?

The **Agent Node** is a specialised Workflow node that wraps an LLM in a tool-calling loop. It handles:

- **Automatic schema generation** — Vellum inspects the Code Execution nodes (or other callables) you connect as tools and generates the JSON Schema the LLM needs to call them. You don't write schemas by hand.
- **Loop logic** — After each LLM response, the node checks whether the model requested a tool call. If it did, it executes the tool, feeds the result back to the LLM, and loops. If the model produced a final answer instead, the loop exits.
- **Iteration safety** — A configurable **max iterations** limit prevents runaway loops.

The Agent Node exposes a single output — the final message from the LLM once it decides it's done — which you can wire into a Final Output node or any downstream node.

<Note>
  The Agent Node internally manages the chat history for the duration of its loop. You don't need to maintain or pass the message history manually.
</Note>

## Setting Up Tools

Tools are the functions the agent can call. You define them by connecting **Code Execution nodes** to the Agent Node's **Tools** input port.

<Steps>
  <Step title="Create a Code Execution node for each tool">
    Add a Code Execution node to the canvas and write the Python or TypeScript function that implements the tool's logic. The function should accept named parameters and return a value. For example:

    ```python
    # Tool: search_web
    def main(query: str) -> str:
        # Your search implementation here
        results = my_search_client.search(query)
        return results.to_markdown()
    ```
  </Step>
  <Step title="Give the tool a name and description">
    In the Code Execution node's configuration panel, fill in the **Tool Name** and **Tool Description** fields. The LLM uses the name and description to decide when to call this tool — write clear, specific descriptions.

    ```
    Name:        search_web
    Description: Search the internet for up-to-date information on a topic.
                 Use this when the user asks about recent events or facts
                 you are not confident about.
    ```
  </Step>
  <Step title="Connect the node to the Agent Node">
    Draw an edge from the Code Execution node's output port to the Agent Node's **Tools** input port. Repeat for each tool you want the agent to have access to.
  </Step>
  <Step title="Review the auto-generated schema">
    Open the Agent Node's configuration panel and inspect the **Tool Schemas** section. Vellum has parsed your function signature and generated the JSON Schema automatically. Adjust parameter descriptions in your code's docstring or type annotations if any schema detail needs clarifying.
  </Step>
</Steps>

<Tip>
  Keep each tool focused on a single responsibility. Agents perform better when tools have narrow, well-described purposes rather than one large "do everything" function.
</Tip>

## The Agent Loop

Once you run the Workflow, the Agent Node executes the following cycle:

<Steps>
  <Step title="LLM receives the prompt and tool schemas">
    The Agent Node sends the system prompt, the user message (from its input), and the JSON schemas of all connected tools to the configured LLM.
  </Step>
  <Step title="LLM decides: respond or call a tool">
    The model either returns a final text response (loop exits) or returns a structured tool-call request specifying which tool to invoke and with what arguments.
  </Step>
  <Step title="Tool executes">
    Vellum routes the tool-call request to the corresponding Code Execution node, runs it with the provided arguments, and captures the return value.
  </Step>
  <Step title="Result is fed back to the LLM">
    The tool result is appended to the conversation as a tool-response message. The LLM sees the full history — original prompt, its tool call, and the result — and produces its next response.
  </Step>
  <Step title="Loop repeats or exits">
    Steps 2–4 repeat until the LLM returns a final answer without requesting a tool call, or until the **max iterations** limit is reached. If the limit is hit before a final answer is produced, the Agent Node raises an error (which you can catch with the Try adornment).
  </Step>
</Steps>

## Common Agent Patterns

### RAG Agent

A Retrieval-Augmented Generation agent combines a **Search tool** with an LLM to answer questions grounded in your documents.

- **Tools**: one `search_documents` tool backed by a Vellum Document Index.
- **System prompt**: instruct the agent to always search before answering and to cite its sources.
- **Flow**: user query → agent searches → agent synthesises answer from retrieved chunks.

### Multi-Step Research Agent

A research agent uses multiple tools to gather information from different sources before writing a comprehensive report.

- **Tools**: `search_web`, `fetch_url`, `search_internal_knowledge_base`.
- **System prompt**: instruct the agent to gather evidence from at least two sources before drafting a response.
- **Flow**: agent plans searches → executes searches in sequence → synthesises findings → returns report.

<Note>
  For research agents, set a generous **max iterations** (e.g., 10–20) to give the agent room to gather enough information before concluding.
</Note>

### Form-Filling Agent

A form-filling agent collects structured information from a user through a conversation and writes it to a downstream system.

- **Tools**: `submit_form(data: dict)` — calls an API Node or Code Execution node that writes to your CRM or database.
- **System prompt**: instruct the agent to collect all required fields before calling `submit_form`, and to ask follow-up questions if information is missing.
- **Flow**: agent asks clarifying questions → user provides answers → agent calls `submit_form` when all fields are collected.

## Configuration Options

### Max Iterations

Set **Max Iterations** in the Agent Node's configuration panel. This is the maximum number of tool-call/response cycles before the node stops and raises an error. Start with a value of 5–10 for most agents and increase it if you observe legitimate tasks being cut short.

### Error Handling with the Try Adornment

Add the **Try adornment** to the Agent Node to catch errors — including max-iteration exhaustion — without stopping the entire Workflow. Wire the **error** output port to a graceful fallback path (e.g., a Final Output node that returns a "I wasn't able to complete this task" message).

```
Agent Node (Try)
├── success → Final Output Node ("answer")
└── error   → Templating Node → Final Output Node ("answer")
                 "I wasn't able to complete this task: {{ error.message }}"
```

### Connecting to Subworkflows

If a tool's logic is complex, implement it as a **Subworkflow Node** rather than a single Code Execution node. The Agent Node treats Subworkflow tools exactly the same way — it calls them with arguments and receives a return value — but the underlying implementation can span multiple nodes.

<Tip>
  Using Subworkflows as tools is also a good way to share tool logic between multiple Agent Nodes without duplicating code.
</Tip>
