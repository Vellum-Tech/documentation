Vellum Environments let you manage the full deployment lifecycle of your AI application — from active experimentation to pre-release QA to live production traffic — without risk of cross-contamination between stages. Each environment is a fully isolated context with its own API keys, deployment release history, execution logs, and Document Indexes. This page explains what environments are, how to work with them, and how to move releases safely from development through to production.

## What Are Environments?

An **Environment** in Vellum is an isolated workspace that scopes all of the following resources independently:

| Resource | Isolated per environment? |
|---|---|
| API keys | ✅ Each environment has its own set of keys. |
| Deployment release history | ✅ You promote a specific release to each environment independently. |
| Execution logs | ✅ Logs are tagged by environment and not shared across them. |
| Document Indexes | ✅ You manage and query separate indexes per environment. |
| Online Evaluator results | ✅ Evaluation runs are scoped to the environment where they executed. |

This isolation means a bad deployment in Development can never affect Production, and the execution logs you see in Staging reflect only the traffic routed there.

## Default Environments

Every Vellum workspace comes with three built-in environments:

| Environment | Intended use |
|---|---|
| **Development** | Active prompt and workflow iteration. Use this environment while building and testing changes. |
| **Staging** | Pre-release QA and integration testing. Mirror production traffic patterns here before going live. |
| **Production** | Live end-user traffic. Only promote releases here after they have passed Staging verification. |

You can also create **custom environments** if your organization needs additional stages (for example, a `canary` environment for gradual rollouts). Navigate to **Settings → Environments → New Environment** to create one.

## Environment API Keys

Each environment has its own API key (or set of keys). Your application uses the key for the environment it is targeting — there is no environment selector in the request body; the key itself determines which environment receives the call.

**To find your API keys:**

<Steps>
  <Step title="Open Settings">
    Click **Settings** in the bottom-left corner of the Vellum UI.
  </Step>
  <Step title="Navigate to API Keys">
    Select **API Keys** from the Settings menu. You will see a list of keys grouped by environment.
  </Step>
  <Step title="Select the environment">
    Click the environment tab (Development, Staging, or Production) to view or copy the key for that environment.
  </Step>
  <Step title="Rotate a key if needed">
    To rotate a compromised or expired key, click **Rotate** next to the key. The old key is immediately invalidated. Update your application's environment variables with the new key before rotating in production to avoid downtime.
  </Step>
</Steps>

<Warning>
  Using the wrong environment's API key in production will route live traffic to a different deployment version than you intend — for example, an unfinished Development release. Always double-check which key is configured in each of your deployment targets.
</Warning>

## Deployment Lifecycle Across Environments

Vellum treats each environment's deployment state independently. Releasing a new prompt or workflow version follows a **promote** pattern rather than a single global deploy:

<Steps>
  <Step title="Deploy to Development">
    When you save and release a new version of a Prompt or Workflow from the editor, it is deployed to your **Development** environment by default. Test it by calling your Development API key or using the Vellum Playground.
  </Step>
  <Step title="Promote to Staging">
    Once the Development release looks good, open the deployment's **Releases** tab, find the release you want to advance, and click **Promote to Staging**. This makes the exact same artifact available under your Staging API key without redeploying or re-configuring anything.
  </Step>
  <Step title="Verify in Staging">
    Run your integration test suite or manual QA against the Staging endpoint. Review execution logs in the Staging environment to confirm outputs and latency meet your requirements.
  </Step>
  <Step title="Promote to Production">
    When Staging verification passes, click **Promote to Production** on the same release. Live traffic immediately begins using the promoted version.
  </Step>
</Steps>

**Promotion vs. redeployment** — Promoting a release copies the already-built artifact to the target environment. Nothing is re-compiled or re-evaluated; you are moving the same release that passed testing. Redeployment (making a new change and deploying it from scratch) starts the cycle over from Development.

## Best Practices

- **Use Development for active experimentation.** Iterate freely — change prompts, swap models, adjust parameters — without worrying about affecting users.
- **Mirror production load in Staging.** Run realistic queries against Staging before promoting, especially after model or prompt changes that could shift output distributions.
- **Never use a Production API key in development code.** Store API keys in environment variables and use separate `.env` files (or secrets manager entries) for each stage of your application.
- **Tag production releases with semantic version labels.** When promoting to Production, add a release tag like `v2.1.0` so you can quickly identify which version is live and roll back to a specific prior release if needed.
- **Rotate keys on a schedule.** Treat API keys like passwords — rotate them periodically and immediately when a key may have been exposed.

<Tip>
  Use your CI/CD pipeline to automate promotion. The Vellum API exposes endpoints to query release status and trigger promotions, so you can gate a Staging → Production promotion on a passing test suite without manual intervention.
</Tip>
